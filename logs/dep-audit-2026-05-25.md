## `next`

- Current: `15.5.12`
- Latest: `16.2.6`
- Category: MAJOR-REFACTOR
- Advisory status: `npm audit` reports direct `next` vulnerabilities, including high-severity middleware/proxy bypass, Server Components denial of service, WebSocket-upgrade SSRF, and related moderate/low issues. Audit reports a non-major security fix path at `15.5.18`; npm latest is `16.2.6`.
- Release notes reviewed:
  - Next 16 upgrade guide: https://nextjs.org/docs/app/guides/upgrading/version-16
  - Next 16 release notes: https://nextjs.org/blog/next-16
  - npm dist-tags checked: `latest=16.2.6`, `backport=15.5.18`

Notes:

- The smallest security-first update appears to be `15.5.18`, based on `npm audit` and the `backport` dist-tag. That would likely be much safer than jumping directly to 16.
- Upgrading all the way to latest requires raising the package engine from `node >=18.0.0` to at least Node `20.9.0`; Next 16 no longer supports Node 18.
- Next 16 removes synchronous access compatibility for request-time APIs (`cookies`, `headers`, `draftMode`, route `params`, and `searchParams`). This repo should scan all app route/page/layout code before moving to 16.
- Turbopack is the default for `next dev` and `next build` in v16. `web/next.config.mjs` does not define a custom webpack config, which lowers risk, but the app should still run a production build under Node 20.9+.
- The `middleware` convention is deprecated in favor of `proxy`. This package exports `./middleware` from `lib/auth/middleware.js`; it should be checked against the consuming Next app's file convention before a v16 upgrade.
- Peer dependency ranges should be revisited if the package is meant to support both Next 15 and 16.

What would need to change:

- For a security-only path: update to `next@15.5.18` and verify the app, without taking the v16 breaking changes.
- For latest: raise runtime requirements to Node 20.9+, run the official codemod, review request API usage, verify middleware/proxy conventions, and run a full Next build.

## `drizzle-orm`

- Current: `^0.44.0`
- Latest: `0.45.2`
- Category: SAFE
- Advisory status: `npm audit` reports a direct high-severity SQL injection advisory, fixed by `drizzle-orm@0.45.2`.
- Release notes reviewed:
  - 0.45.2 changelog: https://raw.githubusercontent.com/drizzle-team/drizzle-orm/main/changelogs/drizzle-orm/0.45.2.md
  - 0.45.1 changelog: https://raw.githubusercontent.com/drizzle-team/drizzle-orm/main/changelogs/drizzle-orm/0.45.1.md
  - 0.45.0 changelog: https://raw.githubusercontent.com/drizzle-team/drizzle-orm/main/changelogs/drizzle-orm/0.45.0.md

Notes:

- The 0.45.2 release fixes escaping for `sql.identifier()` and `sql.as()`, the source of the SQL injection advisory.
- This repo uses `drizzle-orm` heavily for query helpers (`eq`, `and`, `desc`, `asc`, `sql`) and the `better-sqlite3` adapter.
- A source search did not find direct use of `sql.identifier()` or `sql.as()`, so the security fix should not require application code changes.
- Because the current range is `^0.44.0`, npm will not select `0.45.2` automatically for a `0.x` package. A manifest change would be required in a future upgrade PR.

What would need to change:

- Update the dependency range to include `0.45.2`.
- Run DB query smoke tests and migration generation checks after the upgrade. No source-level changes are expected from the reviewed release notes.

## `uuid`

- Current: `^9.0.0`
- Latest: `14.0.0`
- Category: MAJOR-REFACTOR
- Advisory status: `npm audit` reports direct and transitive `uuid` exposure for GHSA-w5hq-g745-h8pq. Current direct `uuid@9.x` is below the fixed range.
- Release notes reviewed:
  - Changelog: https://raw.githubusercontent.com/uuidjs/uuid/main/CHANGELOG.md
  - v14 release: https://github.com/uuidjs/uuid/releases/tag/v14.0.0

Notes:

- The repo imports `v4` as a named ESM import in `lib/tools/create-agent-job.js`, `lib/chat/components/chat-page.jsx`, and `lib/chat/api.js`; that import style is already compatible with modern `uuid`.
- The advisory concerns caller-provided buffers/offsets for v3/v5/v6. This repo appears to use only `v4()` string generation, so application exposure is probably low, but the direct vulnerable package remains present.
- Major releases between 9 and 14 include TypeScript conversion, removal of CommonJS support, browser export changes, and Node support changes.
- v14 expects global `crypto` and drops Node 18 support according to the changelog. This conflicts with the current package engine of `node >=18.0.0`.

What would need to change:

- Decide whether the package can raise its runtime floor to Node 20+. If yes, `uuid@14` is viable with the current ESM named imports.
- If Node 18 support must remain, use the newest fixed version compatible with the desired support matrix rather than latest. That would need a separate compatibility check.
- Run tests or smoke checks for ID creation paths after upgrade.

## `ws`

- Current: `^8.19.0`
- Latest: `8.21.0`
- Category: SAFE
- Advisory status: `npm audit` reports a direct moderate advisory for `ws >=8.0.0 <8.20.1`, fixed by `8.20.1`.
- Release notes reviewed:
  - 8.20.1 release: https://github.com/websockets/ws/releases/tag/8.20.1
  - 8.21.0 release: https://github.com/websockets/ws/releases/tag/8.21.0

Notes:

- The 8.20.1 fix addresses an uninitialized memory disclosure when unsupported `TypedArray` values are passed as the `websocket.close()` reason.
- This repo uses `WebSocketServer`, `WebSocket`, `send`, and `close()` in `lib/code/ws-proxy.js`.
- Source usage calls `close()` without a reason and forwards message payloads; no migration issue is apparent from the reviewed release notes.
- `8.21.0` stays within major version 8, so this should be a low-risk security update.

What would need to change:

- Update to at least `8.20.1`; latest `8.21.0` should be acceptable.
- Smoke test authenticated `/code/{id}/ws` and `/code/{id}/term/{sessionId}/ws` proxy flows.

## `node-cron`

- Current: `^3.0.3`
- Latest: `4.2.1`
- Category: MINOR-CODE-CHANGES
- Advisory status: `npm audit` reports direct `node-cron` exposure via `uuid`, with a fix path to `node-cron@4.2.1`.
- Release notes reviewed:
  - v3 to v4 migration guide: https://nodecron.com/migrating-from-v3
  - v4 scheduling options: https://nodecron.com/scheduling-options
  - API reference: https://nodecron.com/api-reference

Notes:

- v4 is a TypeScript rewrite with a new scheduler implementation.
- Breaking changes include removal of `scheduled` and `runOnInit` options, use of `createTask()` for initially stopped tasks, and changed lifecycle event names.
- Current repo usage in `lib/maintenance.js`, `lib/cluster/runtime.js`, and `lib/cron.js` uses `cron.schedule(...)` and `cron.validate(...)` without removed options or lifecycle event listeners.
- Because current usage is basic, source changes may not be needed, but the scheduler semantics should be tested.

What would need to change:

- Verify that no consuming app passes `scheduled`, `runOnInit`, or v3 event names through configuration.
- Run smoke tests for built-in hourly maintenance/version checks, cluster cron triggers, and `CRONS.json`-loaded jobs.
- If any initially stopped task behavior is needed later, migrate that code to `cron.createTask()`.
