## `next`

- Current version: `15.5.12` in `dependencies`; peer range `>=15.5.12`.
- Latest version: `16.2.6`.
- Category: MAJOR-REFACTOR for latest. A targeted security patch to `15.5.18` should be SAFE/MINOR and is what `npm audit` recommends for the current vulnerable line.
- Security notes: `npm audit` reports direct high-severity Next.js advisories, including middleware/proxy bypasses, Server Components denial of service, WebSocket-upgrade SSRF, image optimization denial of service, cache poisoning, XSS, HTTP request smuggling, and vulnerable transitive `postcss`. The audit fix target is `next@15.5.18`, not the latest major.
- Release notes reviewed:
  - Next.js 16 release: https://nextjs.org/blog/next-16
  - Next.js 16 upgrade guide: https://nextjs.org/docs/app/guides/upgrading/version-16
- What would need to change:
  - For immediate security risk reduction, consider `15.5.12 -> 15.5.18` first; this avoids the major-version migration while addressing the advisories flagged by `npm audit`.
  - For latest `16.2.6`, update `next`, `react`, and `react-dom` together and run the official Next codemod. The v16 guide calls out breaking changes around fully async request APIs, changed `next/image` defaults, sitemap `id` now being a promise, and Turbopack/config migration.
  - This repository uses a custom Next server in `web/server.js` and deliberately sets an internal `app.didWebSocketSetup` flag to bypass Next's WebSocket handling. That is specifically sensitive to Next internals and should be regression-tested after any Next upgrade.
  - The root `engines.node` currently allows `>=18.0.0`. Next 16 beta/release notes indicate Node 18 support has been dropped in the v16 line, so publishing support for Node 18 would need to be revisited before adopting latest.

  - Because this is a `0.x` package, still run smoke tests for DB startup, migrations, and representative chat/config CRUD paths after upgrading.

## `uuid`

- Current version: `^9.0.0`.
- Latest version: `14.0.0`.
- Category: MAJOR-REFACTOR.
- Security notes: direct moderate advisory `GHSA-w5hq-g745-h8pq` for missing buffer bounds checks in v3/v5/v6 when a caller supplies `buf`; `npm audit` also shows this vulnerable package affecting LangChain, LangSmith, and `node-cron` transitive paths.
- Release notes reviewed:
  - `uuid` `14.0.0` release: https://github.com/uuidjs/uuid/releases/tag/v14.0.0
- What would need to change:
  - The local direct usage is simple `import { v4 as uuidv4 } from 'uuid'`, which should be mechanically low-risk.
  - The latest major has platform-breaking changes: it expects global `crypto` and requires Node 20+, dropping Node 18 support. The project currently advertises `node >=18.0.0`, so moving to `uuid@14` requires either raising the engine floor or avoiding latest.
  - A pragmatic security path is to move to a non-latest patched line compatible with the intended engine support if Node 18 must remain supported. If Node 18 support is dropped, `uuid@14` should be tested in both browser-bundled code (`lib/chat/components/chat-page.jsx`) and server code (`lib/chat/api.js`, `lib/tools/create-agent-job.js`).
  - Several server modules already use `crypto.randomUUID()`. The remaining direct `uuid` usages could also be replaced with native `crypto.randomUUID()` where browser support and bundling constraints are acceptable.

## `ws`

- Current version: `^8.19.0`.
- Latest version: `8.21.0`.
- Category: SAFE.
- Security notes: direct moderate advisory `GHSA-58qx-3vcg-4xpx` from `npm audit` for uninitialized memory disclosure in `ws <8.20.1`. The latest `8.21.0` release also fixes a remote memory-exhaustion denial of service and adds `maxBufferedChunks` and `maxFragments` options.
- Release notes reviewed:
  - `ws` `8.21.0` release: https://github.com/websockets/ws/releases/tag/8.21.0
- What would need to change:
  - The project imports `WebSocketServer` and `WebSocket` from `ws` in `lib/code/ws-proxy.js`. That API remains on the same major version.
  - The current server disables per-message deflate with `perMessageDeflate: false`, which reduces compression-related risk.
  - After upgrade, test `/code/*/ws` terminal proxy flows, auth failure handling, and backend ttyd disconnect/reconnect behavior. Consider setting the new fragment/buffer limit options explicitly if hostile WebSocket peers are a concern.

## `node-cron`

- Current version: `^3.0.3`.
- Latest version: `4.2.1`.
- Category: MINOR-CODE-CHANGES.
- Security notes: direct moderate `npm audit` entry via vulnerable transitive `uuid`; audit suggests `node-cron@4.2.1`, a semver-major update.
- Release notes reviewed:
  - `node-cron` `4.0.0` release: https://github.com/node-cron/node-cron/releases/tag/v4.0.0
- What would need to change:
  - v4 release notes describe the v4 migration as a TypeScript rewrite. The public `cron.schedule(...)` shape remains documented in the v4 README, but the major bump means runtime behavior should be verified.
  - This project uses `cron.schedule(...)` in `lib/maintenance.js`, `lib/cron.js`, and `lib/cluster/runtime.js`.
  - Check job lifecycle behavior after upgrade: scheduled tasks should still start as expected, returned task handles should still support `.stop()`, and invalid user-provided cron expressions should be validated consistently.
  - Regression-test hourly maintenance, version check scheduling, user-defined `CRONS.json`, and cluster role trigger scheduling.

## Recommended Upgrade Order

1. Patch `next` to `15.5.18` first if the objective is immediate security reduction with minimal churn.
2. Upgrade `drizzle-orm` to `0.45.2`.
3. Upgrade `ws` to `8.21.0`.
4. Decide whether the package still supports Node 18 before upgrading `uuid` to latest.
5. Upgrade `node-cron` after `uuid`/engine policy is decided, then test all cron-driven flows.
